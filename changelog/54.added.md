Drift detection now sees config the device carries that intent never asked for. The structural diff only ever walked *desired* entities, so an interface or BGP neighbour added by hand and absent from the Source of Truth produced zero drift — the report read CLEAN. The naive fix is dangerous, and the live fabric shows why: a real SR Linux spine reports 31 interfaces intent does not name, of which 30 are unconfigured chassis ports and one is `mgmt0`, whose address is the one snapl dials over. Flagging every extra would bury each scan under hardware inventory; removing them (issue #65) would strand the device permanently. The rule that makes the difference tractable, specified in `specs/007-undesired-config/spec.md`: an entity counts as undesired only when it carries a value-bearing field — `description`, `ip_address`, `prefix_length` or `mtu` for interfaces, the ASN or peer group for neighbours — so a bare chassis port stays invisible while a hand-added IP does not, and `enabled` alone never qualifies since a port being up implies no intent. A protected set (`mgmt0`, `system0`) is never reported and, once removal lands, never deleted. Undesired findings are ordinary `DriftItem`s carrying `undesired=True`, and the CLI renders their desired column as `not in intent` rather than a bare `None`, which otherwise reads identically to intent wanting a field the device has not set — the opposite problem needing the opposite fix. Detection only: nothing this adds can write to a device.
