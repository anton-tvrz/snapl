Dashboard API additions for the designed UI (spec 011): `GET /api/v1/topology` returns the use case's devices and the links their interfaces declare in intent, and `/api/v1/devices` and `/api/v1/runs` accept `at=` to show the state the audit trail recorded up to a past time. `GET /api/v1/drift-timeline` returns one lane of scan points per device and the drift episodes over them, with what repaired each. `GET /api/v1/runs/steps` returns what each NAF block did in one run, as far as the audit trail records it. `GET /api/v1/mode` says whether the server shows the live stack or an archive. The designed dashboard UI's foundation: `uv run invoke dashboard.build` builds it (Node 22.12 or later, only to build), `snapl dashboard` then serves it at `/`, and serves the plain page at `/plain` always and at `/` when the UI is not built. Every response carries a Content-Security-Policy that keeps the browser on the dashboard's own origin. The designed page now draws the fabric: devices in tiers with the links intent declares, each device's drift state by shape, glyph and colour, a ring for work running or just finished, and a dashed link where a drifted path names its interface. Selecting a device opens its detail, and the selection is kept in the page address. The page can replay drift: one lane per device shows each scan's state over time with the reconcile and remediation runs marked, an "as of" control steps through the scans one at a time (kept in the page address), and the topology and device detail show the fabric as it was then. A headline gives the latest repaired drift's duration, from the scan that first saw it to the scan that first saw it gone, and what repaired it. The loop strip shows what each NAF block did in one run (done, failed with its reason, not reached, or not recorded), for the latest run or for one chosen in a device's detail or on a lane's repair marker, and keeps the chosen run in the page address. The designed page now has panels for the drift schedule and the worker, what is running, the recent runs (filtered to the selected device, linked to the Temporal Web UI), and the undesired config across the fabric. At a past time the schedule, worker and running panels say they show only the present. It also has panels for CI (main first, each PR's gate, the failed jobs linked, main's coverage, and the PRs left out without a token) and the live lab evidence (the latest run of each suite, the commits on main since, and incomplete or unreadable runs), and the links to the stack, the repository, the API and the docs. Each of spec 012's six metrics views has a designed panel, with its unit, the step the server used and the latest value of each series as a table: lines for durations and rates, up/down strips for the worker and the sources. A range picker (1 h, 24 h, 7 d or a custom start and end in UTC) sets the range for the metrics and the drift lanes and keeps it in the page address. The designed page also has 010's history table (per hour: scans, the most drifted devices and undesired paths, deploys and repairs, and the repair runs), so every fact on the plain page is on the designed page; a test lists each one and the component that shows it.
