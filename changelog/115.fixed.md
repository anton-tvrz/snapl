snapl can no longer write into a neighbouring project's Source of Truth. An audit of every isolation dimension against `project-network-synapse-quattro` found the port block (#107) and lab subnets (#90) holding up, and two gaps left that are not networking problems. First, both projects shipped the **same** Infrahub admin token, so a misaimed snapl authenticated against the neighbour as admin instead of being refused; snapl now has its own. Because `INFRAHUB_INITIAL_ADMIN_TOKEN` is read only at first boot, an existing stack keeps the old token until `invoke demo.reset` — and any `development/.env` created from the old example needs the new value, or every task fails with `Invalid token`. Second, the identity check added in #107 was wired into `demo.check`, `snapl status` and the e2e refusal — every path that *reports* — but never into the one task that *writes*, and `demo.up` ran `seed` before `check`, so verification happened after the damage. `demo.seed` now identifies the instance before provisioning a schema or seeding. It requires a positive identification rather than merely the absence of a foreign verdict: measured against the real neighbour, `identify` returns UNKNOWN rather than FOREIGN, because that instance will not serve its schema to a stranger — so a guard keyed on `is_foreign` would have let the seed through, which is the exact case it exists to stop. Reporting paths still treat UNKNOWN as inconclusive; only writing demands proof. Verified live: pointed at the neighbour, `demo.seed` refuses before any write; pointed at snapl's own instance it seeds normally. Also pins `name: snapl` in the compose file with a test — without it the project name falls back to the `development` directory, which both repos have, and both declare a volume named `temporal_data`.
