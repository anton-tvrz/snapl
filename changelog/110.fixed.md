The documented demo path now runs on a clean checkout. Three defects surfaced the first time `invoke demo.up` → `orchestrator.start` → `invoke test-e2e` was run end to end against a live stack, none of them visible to the unit suite or CI. `development/.env` was never loaded by the invoke process — docker compose picks it up automatically because it sits beside the compose file, but nothing gave it to the tasks, so `demo.up` died on an unset `INFRAHUB_API_TOKEN` and the worker would have started with neither a token nor a device password; it only ever worked for someone who had already exported the variables by hand. The demo arc never converged the fabric before inducing drift, so on a freshly deployed lab — which boots on its startup config and has never had intent pushed to it — all six devices were legitimately drifted and Scenario 2's "5 clean, 1 drifted" was false; the missing `snapl reconcile --drifted --yes` step is now in both the doc and the arc. And `ScanDrift` recorded its audit events against the use case rather than the device, so `snapl audit --device spine-01` showed the deploy but not the scan that found the drift, contradicting Scenario 8's promise that the per-device query spans scans; each evaluated device now gets its own event carrying status, drift count and paths, with errored devices recorded as `activity_failed`. Also corrects the Scenario 2 drift-injection command, which never executed at all (`sr_cli` parses the quoted `enter candidate; …; commit now` as a single command — `-ec` is the working form), and its stated expectation: drift is reported as `/interface[name=ethernet-1/1]/enabled desired=True actual=False`, against the intent model's field rather than the device's native `admin-state` leaf.
