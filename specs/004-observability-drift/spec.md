# Feature Specification: NAF Observability Block

**Feature Branch**: `004-observability-drift`
**Created**: 2026-05-14
**Status**: Draft
**Input**: NAF Observability building block — drift detection, event emission, and audit logging for the snapl network automation platform.

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Detect Configuration Drift on a Device (Priority: P1)

An operator or automated workflow needs to know whether the live configuration of a network device matches what was intended. The Observability block compares the desired state (from Intent) against the actual running state (from Collector) and produces a structured report of every discrepancy.

**Why this priority**: Drift detection is the core purpose of the Observability block and the primary trigger for the NAF feedback loop. Without it, the platform cannot tell whether previous automation succeeded or whether manual changes have deviated from intent.

**Independent Test**: A drift report for a single device can be generated by providing a desired state object and a collect result object; the report is fully testable in isolation with no infrastructure.

**Acceptance Scenarios**:

1. **Given** a device's desired state from Intent and its live collected state from Collector, **When** drift detection is run, **Then** a DriftReport is returned listing each attribute path where the actual value differs from the desired value, with both values recorded.
2. **Given** a device whose live state exactly matches its desired state, **When** drift detection is run, **Then** a DriftReport is returned with an empty discrepancies list and a `clean` status.
3. **Given** a device whose live state cannot be retrieved (Collector returns an error), **When** drift detection is run, **Then** the DriftReport reflects an `error` status and the discrepancies list is empty; no exception is raised to the caller.
4. **Given** a partially-deployed device (some attributes match, others do not), **When** drift detection is run, **Then** only the non-matching attributes appear in the DriftReport.

---

### User Story 2 — Emit a Drift Event for Downstream Consumers (Priority: P2)

When drift is detected, the Orchestrator (and any other consumer) must be notified so it can decide whether to remediate, alert, or suppress. The Observability block emits structured events that carry the drift context.

**Why this priority**: Events decouple detection from action. The Orchestrator acts on events, not on drift reports directly. Without event emission, each consumer would have to poll or re-run detection independently.

**Independent Test**: An event can be emitted by passing a DriftReport to the emit method; the output is a structured event object verifiable without any event bus or message broker.

**Acceptance Scenarios**:

1. **Given** a DriftReport with one or more discrepancies, **When** an event is emitted, **Then** a structured ObservabilityEvent is returned containing the device identity, event type `drift_detected`, the DriftReport reference, and a UTC timestamp.
2. **Given** a DriftReport with zero discrepancies (clean), **When** an event is emitted, **Then** a structured ObservabilityEvent with event type `state_clean` is returned.
3. **Given** a valid ObservabilityEvent, **When** it is published to any registered handler, **Then** all handlers receive it and none block the caller; failures in one handler do not prevent delivery to others.

---

### User Story 3 — Record an Audit Entry for Every Automation Operation (Priority: P3)

Every significant automation action (config deployment, drift check, rollback) must be logged with enough context to reconstruct what happened, when, by which component, and with what outcome. The audit log is append-only and queryable.

**Why this priority**: Audit logging satisfies operational and compliance requirements. Without it, there is no authoritative record of what the automation did, making troubleshooting and accountability impossible.

**Independent Test**: An audit entry can be created by passing an operation record to the log method; persistence and query are independently testable using in-memory storage in unit tests.

**Acceptance Scenarios**:

1. **Given** a completed automation operation (any type), **When** `log_audit` is called with the operation details, **Then** an AuditEntry is persisted with: operation type, device identity, initiating component, outcome (success/failure), UTC timestamp, and optional detail payload.
2. **Given** a sequence of audit entries for the same device, **When** the audit log is queried by device, **Then** all entries for that device are returned in chronological order.
3. **Given** a persisted AuditEntry, **When** any code attempts to modify it after creation, **Then** the modification is rejected; entries are immutable once written.
4. **Given** a system with no prior audit entries, **When** the log is queried, **Then** an empty result is returned without error.

---

### Edge Cases

- What happens when drift detection receives a desired state with no interfaces or BGP sessions (empty desired config)?
- How does the system handle a device present in Intent but with no corresponding Collector result?
- What happens if the Collector returns data for paths not referenced by the desired state?
- What happens when `emit_event` is called with no registered handlers?
- What happens when the audit storage backend is unavailable at write time?
- What happens when drift detection is invoked concurrently for the same device?

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: The system MUST compare a device's desired state (DesiredState from snapl-intent) against its live collected state (CollectResult from snapl-collector) and produce a DriftReport containing every attribute path where values differ.
- **FR-002**: The system MUST assign each DriftReport a status of `clean`, `drifted`, or `error`, where `error` indicates the live state could not be obtained.
- **FR-003**: Each discrepancy entry in a DriftReport MUST record the attribute path, the desired value, and the actual observed value.
- **FR-004**: The system MUST emit a structured ObservabilityEvent for every completed drift check, regardless of outcome.
- **FR-005**: ObservabilityEvents MUST carry: event type, device identity (ID and name), UTC timestamp, and a reference to the triggering DriftReport.
- **FR-006**: The event emission interface MUST support registering zero or more handlers; calling emit with no handlers MUST succeed silently.
- **FR-007**: The system MUST record an AuditEntry for every invocation of `detect_drift`, capturing the initiating component, target device, and outcome.
- **FR-008**: AuditEntries MUST be immutable after creation.
- **FR-009**: The system MUST support querying the audit log by device ID, returning entries in ascending timestamp order.
- **FR-010**: The Observer ABC MUST be independently importable from snapl-observability with no dependency on concrete infrastructure (no database drivers, message brokers, or network clients at import time).
- **FR-011**: The system MUST support batch drift detection across multiple devices, returning one DriftReport per device.

### Key Entities

- **DriftItem**: A single detected discrepancy — records the attribute path, expected value, and observed value for one out-of-sync attribute on a device.
- **DriftReport**: The complete drift analysis for one device — contains device identity, a list of DriftItems, an overall status (`clean` / `drifted` / `error`), a UTC timestamp, and an optional error detail string.
- **ObservabilityEvent**: A structured notification emitted after a drift check — contains event type, device identity, UTC timestamp, and the associated DriftReport.
- **AuditEntry**: An immutable log record for one automation operation — contains operation type, device identity, initiating component name, outcome, UTC timestamp, and an optional free-form detail payload.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: A drift report for a single device is produced within 100 ms of receiving the desired and actual state inputs (excluding any time spent by the Collector itself).
- **SC-002**: Drift detection correctly identifies 100% of attribute discrepancies across all supported intent model fields (Device, Interface, BGPSession) in unit tests.
- **SC-003**: The Observer ABC and all data models are importable with zero external service connections; unit tests run with no infrastructure.
- **SC-004**: All audit entries are queryable by device with results returned in correct chronological order in 100% of unit test scenarios.
- **SC-005**: Batch drift detection for 10 devices completes with a result for every device, including those where collection failed.
- **SC-006**: Unit test coverage on the observability package reaches ≥ 80%.

## Assumptions

- The Observability block receives pre-fetched CollectResult objects; it does not call the Collector directly. The Orchestrator (or caller) coordinates the Collector invocation before calling `detect_drift`.
- Desired state is provided as a `DesiredState` object from snapl-intent; the Observability block does not query Intent independently.
- Audit storage in this iteration is in-memory (no external database); persistence across process restarts is out of scope and delegated to a future iteration or the Orchestrator layer.
- Event handlers are synchronous callables in this iteration; async event bus integration (e.g., Temporal signals) is an Orchestrator concern and out of scope here.
- Drift comparison is structural (value equality on Pydantic model fields); semantic equivalence (e.g., equivalent CIDR notations) is out of scope for this iteration.
- The Nokia SR Linux lab via Containerlab is the target environment, but the Observability block itself is vendor-agnostic.
- Mobile and web UI concerns are out of scope; the Presentation block consumes Observability outputs separately.
